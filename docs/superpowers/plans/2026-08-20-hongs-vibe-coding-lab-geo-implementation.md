# Hong's Vibe Coding Lab GEO 구현 계획

- 작성일: 2026-08-20
- 상태: 단계 0·1·2·3 완료, 단계 4의 `/llms.txt` 실험 항목 일부 적용
- 대상: `https://www.vibehong.shop` 공개 아카이브
- 범위: 공개 랜딩, 앱 상세 페이지, 앱 메타데이터, 정적 갤러리 동기화, 검색·생성형 엔진 측정

## 1. 목표

이 문서에서 말하는 GEO(Generative Engine Optimization)는 키워드를 반복해 생성형 엔진을 조작하는 작업이 아닙니다. 교사와 학생이 찾는 질문에 대해 사이트가 다음 네 가지를 충족하도록 만드는 작업입니다.

1. 생성형 엔진이 페이지를 안정적으로 발견합니다.
2. 페이지의 핵심 사실을 짧고 명확하게 추출할 수 있습니다.
3. 사실의 출처가 한 페이지 안에서 일관되게 연결됩니다.
4. 답변에 인용될 때 사용자가 확인할 수 있는 원문 URL로 이어집니다.

### 성공 기준

- 앱 상세 페이지마다 `무엇인지`, `누가 쓰는지`, `어떻게 쓰는지`, `무엇을 하는지`를 첫 화면과 HTML 원문에서 확인할 수 있습니다.
- 화면에 보이는 사실과 `title`, `description`, canonical, JSON-LD, sitemap의 사실이 서로 다르지 않습니다.
- 공개 스냅샷에 등록된 앱만 색인되며, 삭제·변경된 앱 URL과 `lastModified`가 일관됩니다.
- 허위 리뷰, 평점, 수상, 사용자 수, 교육 효과를 구조화 데이터에 넣지 않습니다.
- 측정용 질문 세트로 생성형 답변의 언급률보다 먼저 `정확한 인용률`과 `사실 정확도`를 추적합니다.

## 2. 현재 기반과 제약

현재 저장소에는 GEO의 기술적 기반이 이미 있습니다.

- `src/data/public-apps.json`과 `public/app-thumbnails/`를 사용하는 정적 공개 아카이브
- `/apps/[slug]` 앱별 상세 페이지와 정적 파라미터 생성
- `src/app/site-metadata.ts`의 canonical, robots, Open Graph, Google·네이버 인증 토큰
- `src/app/sitemap.ts`, `src/app/robots.ts`
- `src/lib/seo/structured-data.ts`의 `CollectionPage`, `SoftwareApplication`, `BreadcrumbList`
- 관리자 DB 변경과 공개 정적 갤러리 동기화가 분리된 배포 구조
- 앱 레코드의 `summary`, `tags`, `subject`, `grade`, `subjects`, `gradeBands`, `audience`, `interactionType`, `learningProcess`, `memo`
- 접근 가능한 `업데이트 내역` UI

따라서 1차 구현은 새로운 검색 서버나 외부 AI API를 만드는 것이 아니라, 현재 정적 공개 흐름에 사실 중심 콘텐츠와 검증 단계를 추가하는 방향으로 진행합니다.

### 제약 및 원칙

- DB 원문을 공개 API로 노출하지 않습니다. 공개 기준은 배포된 정적 스냅샷입니다.
- 관리자 저장과 공개 반영은 계속 분리합니다. GEO 콘텐츠를 수정한 뒤에는 정적 갤러리 동기화와 배포가 필요합니다.
- 원본 앱, GitHub, 수업 자료 등 외부 링크는 실제로 확인된 경우에만 노출합니다.
- 보이지 않는 키워드 블록, 자동 생성된 근거 없는 FAQ, 가짜 평점·리뷰를 만들지 않습니다.
- 이번 계획에서는 검색 순위나 생성형 답변 노출을 보장한다고 표현하지 않습니다. 측정 가능한 개선 신호를 정의합니다.

## 4. 1차 구현 범위

### 4.1 콘텐츠 계약 고정

기존 필드를 재사용하되, 관리자 입력과 공개 문장에 아래 의미를 고정합니다.

| 질문 | 사용 필드 | 작성 규칙 |
|---|---|---|
| 무엇인가요? | `title`, `summary` | 대상과 핵심 작업이 들어간 한두 문장 |
| 누구를 위한 것인가요? | `audience`, `grade`, `gradeBands` | 교사·학생·교사와 학생을 구분 |
| 어떤 교과·주제인가요? | `subject`, `subjects`, `tags` | 실제 화면 또는 수업 자료에서 확인된 값만 사용 |
| 어떻게 활용하나요? | `memo`, `learningProcess` | 시작 행동부터 결과 확인까지 순서가 드러나도록 작성 |
| 어떤 상호작용인가요? | `interactionType` | 연습·탐색·제작·기록 등 현재 허용값을 사용 |
| 언제 수정되었나요? | `updatedAt` | 공개 사실이 바뀔 때 반드시 갱신 |

기존 데이터에 새 컬럼을 바로 추가하지 않고, 먼저 이 계약으로 현황을 검사합니다. 검사 결과 반복적으로 부족한 항목이 확인될 때만 2차로 `useCases`, `howToUse` 같은 구조화 필드를 추가합니다. 이 순서가 현재 DB·정적 export·관리자 폼의 변경량을 최소화합니다.

### 4.2 앱 상세 페이지의 답변 블록

대상 파일: `src/features/app-detail/app-detail-page.tsx` 및 스타일·테스트 파일

현재 제목·요약·태그·메모 중심 화면을 아래의 읽기 순서로 확장합니다.

1. `h1`: 앱의 공식 제목
2. 한 문장 요약: `summary`
3. `한눈에 보기`: 대상, 교과, 학년, 상호작용
4. `이 앱으로 할 수 있는 일`: `learningProcess`와 사실 기반 설명
5. `수업과 업무에서 활용하는 방법`: `memo`
6. `원본 앱 열기`: 실제 앱 URL
7. 관련 앱
8. 최근 정보 수정일과 `업데이트 내역`

각 블록은 일반 사용자에게 보이는 HTML이어야 합니다. JSON-LD에만 존재하는 질문·답변을 만들지 않습니다.

### 4.3 브랜드·사이트 엔터티 정리

대상 파일: `src/lib/seo/structured-data.ts`, `src/app/page.tsx`, `src/app/layout.tsx`, `src/app/site-metadata.ts`

- 홈에 `Organization`과 `WebSite`를 포함한 사이트 엔터티 그래프를 추가합니다.
- `Hong's Vibe Coding Lab`의 이름, 설명, 사이트 URL, 로고는 현재 실제 공개 자산으로만 구성합니다.
- 공식 프로필이나 저장소가 확인될 때만 `sameAs`에 추가합니다.
- 앱 상세에는 기존 `SoftwareApplication`과 `BreadcrumbList`를 유지하고, `audience`, `educationalLevel` 등은 실제 필드가 있을 때만 넣습니다.
- FAQ 구조화 데이터는 화면에 실제로 보이는 FAQ가 있을 때만 추가합니다.
- `aggregateRating`, `review`, `offers`, `interactionStatistic`은 근거 데이터가 생기기 전까지 넣지 않습니다.

권장 구조는 다음과 같습니다.

```text
홈
└── @graph
    ├── Organization
    ├── WebSite
    └── CollectionPage
        └── ItemList ──> /apps/{slug}

앱 상세
└── @graph
    ├── SoftwareApplication
    ├── BreadcrumbList
    └── FAQPage (화면에 실제 FAQ가 있을 때만)
```

### 4.4 크롤링·색인 일관성

대상 파일: `src/app/sitemap.ts`, `src/app/robots.ts`, `src/app/apps/[slug]/page.tsx`, 관련 테스트

- 공개 스냅샷의 모든 앱 상세 URL이 sitemap에 한 번씩만 포함되는지 검사합니다.
- canonical, sitemap URL, JSON-LD URL, 화면의 앱 경로가 같은 slug 규칙을 쓰는지 검사합니다.
- 삭제되거나 존재하지 않는 slug는 `notFound()`와 `noindex` 동작을 유지합니다.
- `updatedAt`는 단순 DB 저장 시간이 아니라 공개 사실의 최종 수정일로 관리합니다.
- `/admin`, `/api`는 계속 robots에서 제외하고, robots 차단이 보안 장치가 아님을 문서에 남깁니다.
- 필요하면 `/llms.txt`를 별도 실험 항목으로 검토하되, 핵심 색인·인용 전략으로 의존하지 않습니다.

### 4.5 관리자 입력 품질 보조

대상 파일: `src/features/admin/app-form.tsx`, 앱 입력 스키마, 관리자 테스트

관리자 화면에 “생성형 엔진이 읽기 쉬운 공개 정보”라는 짧은 안내와 입력 보조를 추가합니다.

- `summary`: “누가 무엇을 하기 위한 앱인지”를 작성하도록 placeholder와 도움말 제공
- `memo`: 수업·업무에서의 실제 활용 흐름을 작성하도록 안내
- `learningProcess`: 쉼표 구분 값의 중복·공백 정리
- `audience`, `gradeBands`, `subjects`: 허용값과 표시값을 명확히 구분
- 필수 사실이 비어 있으면 저장을 막을지, 관리자 경고만 표시할지는 데이터 감사 후 결정

초기에는 기존 앱 등록을 깨지 않도록 경고 우선으로 적용하고, 신규 등록부터 계약을 강화합니다.

## 5. 구현 단계

### 단계 0 — 기준선 감사

1. 현재 정적 스냅샷의 앱 수, slug, 필드 누락, 중복 태그를 보고서로 생성합니다.
2. 대표 앱 10개를 선정해 실제 공개 페이지의 제목·요약·대상·사용 방법이 원본 앱과 일치하는지 수동 확인합니다.
3. 브랜드·카테고리·교과·사용 상황별 GEO 질문 세트를 작성합니다.
4. 기준선 보고서에는 검색 노출을 추정하지 않고, 현재 페이지가 질문에 답할 수 있는지를 기록합니다.

예상 산출물:

- `docs/geo/2026-08-20-content-baseline.md`
- `docs/geo/query-set.md`
- `scripts/verify-geo-content.mjs`와 테스트

### 단계 1 — 사이트·앱 구조화 데이터 보강

1. 사이트 엔터티 그래프 생성 함수를 추가합니다.
2. 홈과 앱 상세에 그래프를 연결합니다.
3. 앱 필드가 비어 있을 때 JSON-LD에서 해당 속성을 생략합니다.
4. JSON-LD 직렬화 보안 테스트를 유지합니다.
5. schema.org 속성·타입을 실제 화면의 사실과 대조하는 테스트 fixture를 추가합니다.

### 단계 2 — 공개 페이지 답변 구조 개선

1. 앱 상세의 `한눈에 보기`, 활용 방법, 활동 과정 영역을 추가합니다.
2. 사실이 없는 영역은 빈 문구나 추측으로 채우지 않고 숨깁니다.
3. 홈에는 아카이브가 어떤 교사용 웹앱을 모아 두었는지 설명하는 짧은 소개를 추가합니다.
4. 제목 계층, 링크 텍스트, 이미지 대체 텍스트, 모바일 줄바꿈을 검증합니다.
5. 기존 `업데이트 내역` 버튼에 이번 GEO 개선 날짜와 요약을 추가합니다.

### 단계 3 — 관리자 품질 루프와 정적 동기화 연계

1. 저장 전 입력 정규화와 누락 경고를 추가합니다.
2. `apps:export-static-gallery` 전에 GEO 콘텐츠 검사를 실행합니다.
3. 실패 시 정적 스냅샷·커밋·배포를 진행하지 않습니다.
4. 성공한 정적 스냅샷에만 공개 배포를 허용합니다.
5. 기존 DB/스냅샷 개수 검증과 asset manifest 검증을 그대로 유지합니다.

### 단계 4 — 엔터티 신뢰 자산 확장

핵심 페이지가 안정화된 뒤에만 진행합니다.

- 사실 기반 `/about` 또는 `/about/hongs-vibe-coding-lab` 소개 페이지
- 공개된 공식 GitHub·프로젝트 페이지와의 상호 링크
- 앱별 원본 저장소·문서 링크가 실제로 있는 경우에만 노출
- 변경 이력과 콘텐츠 검토 기준 문서화
- `/llms.txt` 실험 및 접근 로그 확인

이 단계는 사이트 내부 구조보다 외부에서 확인 가능한 동일성·출처를 강화하는 단계이며, 자동 노출 보장 기능으로 설명하지 않습니다.

### 단계 5 — 측정과 반복 개선

1. 기준선 질문 세트를 동일한 문장으로 다시 실행합니다.
2. 엔진·날짜·질문·답변·인용 URL·정확성·누락 사실을 기록합니다.
3. 틀린 답변이 있으면 키워드를 늘리기 전에 원문 페이지의 사실 구조를 수정합니다.
4. 수정일과 배포 SHA를 보고서에 함께 기록합니다.
5. 월 1회 또는 주요 앱 묶음 배포 후 재측정합니다.

## 6. 측정 지표

생성형 엔진의 내부 랭킹은 직접 통제할 수 없으므로 한 개의 “GEO 점수”로 결론 내리지 않습니다.

| 지표 | 정의 | 1차 목표 |
|---|---|---|
| 사실 완성도 | 필수 질문에 답하는 공개 필드 비율 | 대표 앱 100% |
| 인용 정확도 | 인용된 URL이 실제 답변을 뒷받침하는 비율 | 100% 지향 |
| 답변 정확도 | 앱 이름·대상·기능·사용법이 원문과 맞는 비율 | 100% 지향 |
| 인용 가능성 | 질문 세트 답변에 사이트 URL이 포함된 비율 | 기준선 대비 개선 |
| 색인 건전성 | sitemap URL, canonical, 실제 공개 URL의 일치율 | 100% |
| 신선도 | 콘텐츠 변경 후 `updatedAt`·sitemap·배포 반영 여부 | 100% |

### 질문 세트 구성

초기 24개를 권장합니다.

```text
브랜드 4개   : Hong's Vibe Coding Lab이 무엇인가?
카테고리 4개 : 교사용 웹앱, 초등 수업 도구를 찾는 질문
교과 6개     : 영어·과학·사회·국어·수학·공통
사용 상황 6개: 형성평가·반복 연습·자료 변환·기록·탐색·수업 준비
앱 직접 4개  : 특정 앱의 기능·대상·사용법 질문
```

측정 기록에는 API 키나 개인 정보를 저장하지 않습니다. 외부 엔진의 화면 캡처나 답변을 보관할 때는 서비스 약관과 필요한 최소 범위를 확인합니다.

## 8. 테스트 및 검증 설계

```text
입력 스키마 테스트
        │
        ▼
콘텐츠 계약 검사 ── 실패 ──> 동기화·배포 중단
        │ 성공
        ▼
정적 스냅샷 export
        │
        ├── sitemap / robots / canonical 검사
        ├── JSON-LD 타입·URL·조건부 필드 검사
        ├── HTML heading·답변 블록 검사
        └── 기존 asset·DB 일치 검사
                │
                ▼
        unit → E2E → build → 공개 URL smoke → GEO 질문 재측정
```

### 자동 검증

- 구조화 데이터: 타입, URL, 이름, 설명, 날짜, breadcrumb, 조건부 속성
- 콘텐츠: 빈 제목·요약·URL, 중복 slug, 지나치게 짧은 요약, 허용되지 않은 주장 표식
- 크롤링: sitemap 중복·누락, canonical 불일치, `robots.txt`의 공개 경로 차단
- 회귀: 앱 상세의 답변 영역, 모바일 레이아웃, 외부 앱 열기, 업데이트 내역 모달
- 보안: JSON-LD `</script>` 이스케이프, 관리자/API 비공개, 외부 URL 정규화

### 실행할 검증 명령

```bash
npm run test
npm run lint
npm run build
npm run apps:verify-static-gallery
npm run test:e2e
```

배포 후에는 반드시 실제 공개 주소에서 다음을 확인합니다.

1. `/`, 대표 앱 상세 URL, `/robots.txt`, `/sitemap.xml` HTTP 응답
2. 페이지 원문에 답변 블록·canonical·JSON-LD 존재
3. 앱 열기 버튼과 모바일 화면 동작
4. 업데이트 날짜와 공개 스냅샷 개수
5. 대표 질문 세트 재측정 결과

## 9. 릴리스 게이트

다음 조건을 모두 만족하기 전에는 GEO 완료로 보고하지 않습니다.

- 기준선 보고서와 변경 후 보고서가 있습니다.
- 정적 스냅샷과 관리자 DB의 앱 수·필드·순서가 일치합니다.
- 구조화 데이터 테스트와 콘텐츠 계약 검사를 통과합니다.
- `npm run test`, `npm run lint`, `npm run build`, E2E가 통과합니다.
- 공개 URL에서 대표 앱의 실제 학습·업무 흐름을 확인했습니다.
- `업데이트 내역`에 구현일·개선일과 요약이 기록되어 있습니다.
- 커밋 SHA, CI run, 배포 URL, 대표 URL smoke 결과가 서로 같은 릴리스를 가리킵니다.
- 생성형 답변 측정은 “노출 보장”이 아니라 사실 정확도·인용 정확도 개선 자료로 보고됩니다.

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| 키워드만 늘려 문장이 부자연스러워짐 | 질문에 직접 답하는 문장과 화면 가독성을 우선 |
| JSON-LD와 화면 내용이 달라짐 | 화면에서 파생되는 단일 데이터 함수와 fixture 테스트 사용 |
| FAQ를 자동 생성하면서 근거 없는 답변이 생김 | 보이는 FAQ만 구조화하고, 필드가 없으면 생성하지 않음 |
| `updatedAt`가 저장 시각과 콘텐츠 검토 시각을 혼동 | 공개 사실이 바뀐 경우에만 갱신한다는 운영 규칙 고정 |
| 정적 export 전후 데이터가 달라짐 | export 직전 콘텐츠 계약 검사와 기존 snapshot verifier 재사용 |
| 특정 생성형 엔진 변화에 과적합 | 여러 의도·여러 엔진·고정 질문 세트를 사용하고 월별 비교 |
| 검색 인증 토큰·관리자 정보가 공개됨 | 기존 서버 전용 환경변수와 robots 경계를 유지 |
| `llms.txt`에 과도하게 의존 | 핵심은 HTML·canonical·sitemap·JSON-LD로 유지 |

## 11. 착수 전 결정 항목

권장 기본값은 문서에 반영했습니다.

1. 1차 대상은 전체 공개 앱인가요, 대표 앱 10개 파일럿인가요?
   - 권장: 대표 앱 10개로 콘텐츠 계약과 측정 루프를 먼저 검증한 뒤 전체 확장
2. `about` 엔터티 페이지를 1차에 포함할까요?
   - 권장: 사이트·앱 구조와 콘텐츠 품질이 안정된 뒤 2차에 포함
3. 새 DB 필드를 바로 추가할까요?
   - 권장: 기존 필드 감사 후 반복적인 누락이 확인될 때만 추가
4. `/llms.txt`를 핵심 산출물로 볼까요?
   - 권장: 선택적 실험으로만 진행하고 핵심 릴리스 게이트에는 넣지 않음

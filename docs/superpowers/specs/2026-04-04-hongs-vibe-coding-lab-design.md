# Hong's Vibe Coding Lab 설계 문서

## 1. 문서 개요

`Hong's Vibe Coding Lab`은 선생님이 직접 만든 웹앱을 소개하는 공개 포트폴리오 사이트입니다. 사이트의 핵심 목적은 작품을 보기 좋게 정리해 보여주는 것과, 앞으로 새 웹앱을 계속 쉽게 추가할 수 있도록 관리자 페이지를 제공하는 것입니다.

이 프로젝트의 첫 버전은 다음 네 가지를 우선합니다.

- 공개 사이트가 한눈에 보기 좋고 세련되어 보일 것
- 방문자가 검색과 태그 클릭만으로 원하는 앱을 빠르게 찾을 수 있을 것
- 관리자 페이지에서 새 앱을 간단히 등록, 수정, 삭제할 수 있을 것
- `Vercel`에 배포하기 쉬운 구조일 것

## 2. 합의된 요구사항 요약

### 2.1 공개 사이트 방향

- 구조는 `앱 목록 중심의 쇼케이스형 1안`으로 간다
- 작품 상세 페이지는 v1에 넣지 않는다
- 공개 페이지에는 앱 목록만 두고, 소개/철학/문의 같은 별도 섹션은 넣지 않는다
- 각 앱 카드는 등록된 링크로 바로 이동한다

### 2.2 디자인 방향

- 전체 무드는 `C. 미니멀 아카이브형`으로 간다
- 화려한 랜딩페이지 느낌보다는 차분하고 정돈된 디지털 아카이브처럼 보여야 한다
- `Hong` 캐릭터는 메인 주인공이 아니라 보조 안내 마스코트로 사용한다
- 캐릭터는 검색 안내, 빈 결과 상태, 관리자 도움말 같은 순간에만 절제해서 등장시킨다

### 2.3 관리자 방향

- 관리자 페이지는 1인 운영 기준으로 설계한다
- 로그인은 `관리자 비밀번호 1개` 방식으로 간단히 처리한다
- 앱 등록 시 기본 입력 항목은 단순하게 유지한다
- `subject`, `grade`, `memo`는 선택 입력으로 두되, 입력된 경우 공개 사이트에도 노출한다
- `tags`는 여러 개 입력할 수 있어야 한다

### 2.4 썸네일 방향

- 앱 링크를 입력하면 썸네일을 자동으로 가져오는 기능을 제공한다
- 자동 수집이 실패하면 아래 두 가지를 모두 허용한다
  - 직접 이미지 업로드
  - 기본 플레이스홀더 이미지 사용

## 3. 제품 목표

- 선생님이 만든 교육용 웹앱을 신뢰감 있고 보기 좋게 소개한다
- 방문자가 작품을 빠르게 훑고 바로 사용해 볼 수 있게 만든다
- 새 앱을 추가할 때 코드 수정 없이 관리자 페이지에서 처리할 수 있게 만든다
- 운영이 길어져도 부담이 적은 구조로 시작한다

## 4. 비목표

첫 버전에서는 아래 항목을 범위에서 제외한다.

- 다중 관리자
- 공개용 앱 상세 페이지
- 블로그, 긴 자기소개, 철학 섹션
- 외부 CMS 도입
- 복잡한 권한 체계

## 5. 기술 방향

### 5.1 권장 스택

- 프레임워크: `Next.js`
- 배포: `Vercel`
- 데이터 저장: `Postgres`
- 이미지 저장: `Vercel Blob`
- 인증: 환경변수 기반 관리자 비밀번호 + 서명된 세션 쿠키

### 5.2 이 방향을 선택한 이유

이 구조는 다음 균형이 좋습니다.

- 커스텀 디자인 자유도가 높다
- 공개 사이트와 관리자 페이지를 한 프로젝트 안에서 함께 운영할 수 있다
- 이후 앱 수가 늘어나도 파일 기반보다 안정적이다
- `Vercel` 배포와 운영 흐름에 잘 맞는다

## 6. 정보 구조

### 6.1 공개 라우트

- `/`
  - 메인 아카이브 페이지
  - 검색창
  - 태그 필터
  - 앱 카드 목록

### 6.2 관리자 라우트

- `/admin/login`
  - 비밀번호 로그인 화면
- `/admin`
  - 앱 목록
  - 새 앱 등록
  - 앱 수정
  - 앱 삭제

## 7. 공개 페이지 설계

### 7.1 첫 화면 구조

메인 페이지는 긴 소개보다 바로 작품을 보여주는 구조가 맞습니다. 첫 화면에는 아래 요소가 바로 보여야 합니다.

- 짧은 헤드라인
- 간단한 보조 문구
- 검색창
- 대표 태그
- 앱 카드 목록

소개 문구는 짧고 절제되게 두고, 페이지의 중심은 언제나 앱 카드 목록이어야 합니다.

### 7.2 앱 카드 구성

각 앱 카드는 아래 정보를 담습니다.

- 썸네일
- 제목
- 한 줄 설명
- 태그 여러 개
- 앱 열기 버튼
- 선택 공개 정보
  - 과목(`subject`)
  - 학년(`grade`)
- 선택 공개 메모(`memo`)

### 7.3 공개 메모 표시 방식

`memo`는 비공개 관리자 메모가 아니라 공개용 메모입니다. 다만 카드가 복잡해 보이지 않도록 아래처럼 절제해 보여주는 것이 좋습니다.

- 짧은 미리보기 한두 줄
- `메이커 노트 보기` 같은 가벼운 펼침 패턴

즉, 입력하면 공개하되 카드 전체를 무겁게 만들지는 않는 방향입니다.

### 7.4 검색 동작

검색은 아래 필드를 모두 대상으로 합니다.

- `title`
- `summary`
- `tags`
- `subject`
- `grade`
- `memo`

초기 데이터 규모를 고려하면, 앱 목록을 한 번 불러온 뒤 클라이언트에서 즉시 필터링하는 방식이 가장 자연스럽습니다.

### 7.5 태그 동작

- 앱 하나에는 여러 개의 태그를 등록할 수 있다
- 사용자는 공개 페이지에서 태그를 클릭해 필터링할 수 있다
- 활성화된 태그는 시각적으로 분명히 보여야 한다
- 검색어와 태그 필터는 함께 동작해야 한다

첫 버전의 필터 규칙은 아래처럼 정의합니다.

- 여러 태그를 동시에 선택할 수 있다
- 여러 태그를 선택한 경우 `모든 태그를 포함하는 앱`만 보여준다

이 방식이 방문자가 결과를 좁혀 가기에 가장 직관적입니다.

### 7.6 카드 링크 동작

앱 카드의 주요 CTA는 등록된 앱 링크를 여는 것입니다. 공개 사이트에서 포트폴리오를 탐색하다가 실제 작품으로 넘어가는 흐름이 끊기지 않도록, 앱 열기 버튼은 새 탭으로 여는 방식이 적절합니다.

### 7.7 빈 결과 상태

검색 결과가 없을 때는 빈 상태를 단순 오류처럼 보이지 않게 처리합니다.

- 결과 없음 메시지 노출
- 검색어나 태그를 바꿔보라는 가이드 제공
- `Hong` 캐릭터를 조용히 배치해 친절한 느낌 제공

## 8. 관리자 페이지 설계

### 8.1 인증 모델

v1은 1인 관리자 기준입니다.

- 관리자 비밀번호 1개 사용
- 비밀번호는 환경변수에 저장
- 로그인 성공 시 서명된 세션 쿠키 발급
- `/admin` 이하 경로는 세션이 있어야 접근 가능
- 로그아웃 시 세션 무효화

### 8.2 관리자 메인 화면

관리자 메인에서는 현재 등록된 앱 목록이 보여야 하며, 다음 작업이 빠르게 가능해야 합니다.

- 새 앱 등록
- 앱 수정
- 앱 삭제

불필요한 통계나 복잡한 대시보드보다는 “지금 등록된 작품을 관리하는 화면”에 집중하는 것이 맞습니다.

### 8.3 앱 등록 폼

처음 보이는 기본 입력 항목:

- 제목
- 한 줄 설명
- 링크
- 태그
- 썸네일 설정

선택 입력 영역:

- 과목
- 학년
- 메모

이 구조는 자주 쓰는 입력은 빠르게 처리하고, 필요할 때만 추가 정보를 넣을 수 있게 합니다.

### 8.4 태그 입력 방식

태그는 여러 개 입력할 수 있어야 하므로, 관리자 UI에서는 아래 중 하나가 적합합니다.

- 칩 형태 입력
- 엔터로 확정되는 토큰 입력

핵심은 여러 태그를 넣고 수정하고 삭제하는 흐름이 빠르고 직관적이어야 한다는 점입니다.

## 9. 썸네일 자동 수집 설계

### 9.1 기본 흐름

선생님이 앱 링크를 입력하면 서버가 대상 페이지의 메타데이터를 읽습니다. 이때 우선적으로 찾는 값은 아래와 같습니다.

- 페이지 제목
- 설명
- `og:image`

자동 수집이 성공하면 관리자 폼에 썸네일 미리보기와 제안값을 보여주고, 그대로 쓰거나 수정할 수 있게 합니다.

### 9.2 실패 시 대체 흐름

자동 수집이 실패해도 앱 등록은 계속 가능해야 합니다. 실패 시 아래 두 경로를 모두 제공해야 합니다.

- 직접 이미지 업로드
- 기본 플레이스홀더 이미지 사용

즉, `메타데이터 수집 실패`와 `앱 저장 실패`는 분리해서 다룹니다.

### 9.3 저장 전략

외부 페이지에서 찾은 `og:image`를 그대로 핫링크하면 원본 사이트 상태에 따라 카드가 깨질 수 있습니다. 따라서 가능하면 안정적인 저장 경로를 확보하는 쪽이 좋습니다. 제품 요구사항 관점에서는 다음이 핵심입니다.

- 공개 카드 썸네일이 나중에 사라지지 않아야 한다
- 외부 사이트 상태에 덜 의존해야 한다

## 10. 데이터 구조

첫 버전은 `apps` 중심의 단순한 구조로 시작합니다.

### 10.1 앱 레코드

- `id`
- `title`
- `summary`
- `url`
- `tags` 배열
- `thumbnailMode`
  - `auto`
  - `upload`
  - `placeholder`
- `thumbnailUrl`
- `subject` 선택 공개 필드
- `grade` 선택 공개 필드
- `memo` 선택 공개 필드
- `createdAt`
- `updatedAt`

이 구조는 현재 합의된 범위에 충분하며, 너무 이른 시점에 모델을 복잡하게 나누지 않는 장점이 있습니다.

## 11. 시각 시스템 원칙

### 11.1 시각 목표

- 정돈되고 세련된 인상
- 과한 마케팅 톤 배제
- 앱 자체가 중심이 되는 레이아웃
- 캐릭터는 보조적 사용

### 11.2 시각 특징

- 절제된 색상 체계
- 넉넉한 여백
- 높은 가독성
- 카드 중심 계층 구조
- 과하지 않은 움직임

### 11.3 캐릭터 사용 원칙

`Hong` 캐릭터는 브랜드 정체성을 돕는 장치이지만, 메인 시선을 빼앗는 방식으로 쓰지 않습니다.

권장 사용 위치:

- 검색 안내
- 빈 결과 상태
- 관리자 도움말
- 짧은 말풍선형 가이드

## 12. 반응형과 접근성

### 12.1 반응형

- 모바일에서도 검색과 태그 클릭이 쉬워야 한다
- 카드 그리드는 작은 화면에서 자연스럽게 세로 스택으로 정리되어야 한다
- 관리자 폼도 모바일에서 입력 가능해야 한다

### 12.2 접근성

- 키보드로 검색과 태그 조작 가능
- 포커스 상태가 분명할 것
- 충분한 대비
- 버튼/링크 라벨 명확화
- 썸네일과 캐릭터 이미지의 대체 텍스트 전략 확보

## 13. 오류 처리 설계

### 13.1 공개 페이지

- 썸네일이 없으면 플레이스홀더 사용
- 이미지 로드 실패 시 카드 레이아웃이 깨지지 않게 처리
- 검색 결과가 없을 때는 의도된 빈 상태 화면 노출

### 13.2 관리자 페이지

- 비밀번호 오류 시 일반적인 실패 메시지만 표시
- 메타데이터 수집 실패 시 수동 업로드/플레이스홀더 선택지 제공
- 필수값이 충족되면 자동 수집 실패만으로 저장을 막지 않음
- 삭제는 반드시 확인 단계를 거침

## 14. 검증 범위

첫 구현에서는 아래 항목을 검증해야 합니다.

- 공개 페이지 렌더링
- 검색 동작
- 태그 클릭 필터 동작
- 여러 태그 노출 및 필터링
- `subject`, `grade`, `memo`가 입력된 경우 공개 노출
- 관리자 로그인
- 앱 등록
- 앱 수정
- 앱 삭제
- 메타데이터 수집 성공 흐름
- 메타데이터 수집 실패 후 업로드/플레이스홀더 대체 흐름

## 15. 최종 정리

이 프로젝트의 첫 버전은 “보기 좋고, 빠르게 찾을 수 있고, 계속 추가하기 쉬운 교사용 앱 아카이브”를 만드는 데 집중합니다.

핵심 성격은 아래와 같습니다.

- 공개 사이트: 미니멀 아카이브형 쇼케이스
- 관리자 경험: 1인 운영에 맞춘 간단한 등록 도구
- 데이터 구조: 과하지 않게 단순한 `apps` 중심 설계
- 브랜딩: 차분한 전문성 + 절제된 캐릭터 활용

이 문서는 v1 구현 범위를 고정하기 위한 기준 문서이며, 이후 구현 계획은 이 합의 범위를 전제로 작성합니다.

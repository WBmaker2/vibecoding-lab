# HVC UI/UX 전환 분석 보고서

작성일: 2026-09-07 · 범위: 분석·구현 결과 · 배포 미실시

## 1. 판단

HVC는 **작품을 차례로 둘러보는 아카이브에서, 수업에 맞는 도구를 찾아 다시 사용하는 자료실로 전환**하는 것이 적합합니다. 관리자 페이지는 **등록 폼 중심에서 검색 가능한 앱 목록 중심으로 전환**하는 것을 권합니다.

현재의 밝은 색상, Hong 캐릭터, 앱 미리보기, 직접 실행 링크는 유지할 가치가 있습니다. 우선 바꿔야 할 것은 장식보다 탐색 순서, 분류, 편집 동선입니다.

## 2. 조사 근거와 한계

- 공개 서비스: https://www.vibehong.shop/ — ego-browser로 데스크톱 화면, 검색, 태그 펼침 및 좁은 화면을 관찰했습니다.
- 관리자 진입: https://www.vibehong.shop/admin — 최초 조사 후 사용자 요청으로 로그인하여 내부 화면·앱 선택·미저장 입력 전환·375px 화면을 추가 확인했습니다. 저장·삭제·동기화는 실행하지 않았습니다. 실제 관찰을 11절에 추가했습니다.
- 로컬 공개 스냅샷: `src/data/public-apps.json`, 생성 시각 2026-09-01T09:45:55.971Z. 공개 화면·로컬·관리자 표시 모두 114개입니다. 관리자에는 동기화 대기 없음이 표시됐습니다. 별도의 전체 DB/스냅샷 내용 비교 검증을 실행한 것은 아닙니다.
- Linear: `vibecoding`, `HVC` 검색 결과와 접근 가능한 프로젝트 목록이 비어 있었습니다. 연결 범위 밖에 기록이 있는지는 알 수 없습니다. 이슈·프로젝트는 생성하지 않았습니다.
- 실제 교사 인터뷰, 이용 로그, 전체 앱의 실행 품질, 정식 성능 측정은 이번 분석에 포함되지 않았습니다. 아래 사용성 효과와 목표치는 검증할 가설입니다.
- 좁은 화면은 브라우저 에뮬레이션 관찰입니다. 최초 공개 페이지 조사의 모바일 길이·검색 결과 측정치는 갱신 일관성 문제로 제외했습니다. 추가 관리자 조사에서는 375px 설정 후 별도 호출로 갱신을 확인하고 DOM 측정과 스크린샷을 함께 남겼습니다. 실제 모바일 기기 검증은 후속 과제입니다.

## 3. 114개 데이터가 보여 주는 문제

| 확인 항목 | 현재 값 | 의미 |
|---|---:|---|
| 공개 앱 | 114개 | 전체 나열보다 목적별 탐색이 중요해진 규모 |
| 고유 태그 | 94개 | 한꺼번에 펼치는 태그 목록의 선택 부담 |
| 구조화된 과목 표기 | 24종 | 표준 교과와 주제가 혼재 |
| 학생 / 혼합 / 교사 대상 | 96 / 11 / 7개 | 학생 수업용이 중심이지만 교사 도구의 별도 입구도 필요 |
| 학년군 없음 | 3개 | 학년 필터 도입 전에 적합성 확인 필요 |
| 과학 / 수학 과목 포함 | 29 / 28개 | 주요 과목 안에서도 한 번 더 좁혀야 함 |

과목·학년군은 복수 선택 데이터이므로 범주별 건수를 합하면 전체보다 커질 수 있습니다. 대상 분류에는 자동 추론 결과가 들어갈 수 있어, 위 수치를 교사 검수 완료 데이터로 간주하면 안 됩니다.

구체적인 정비 사례:

- `바른생활`과 `바른 생활`이 별도로 존재합니다. 교과 표준명을 정하고 기존 표현은 검색 동의어로 보존합니다.
- `디지털 시민성`, `환경`, `바이브코딩` 등은 표준 교과와 주제의 관계를 정리합니다. 기존 태그를 일괄 삭제하지 않습니다.
- ‘파이썬 한입 교실’은 `grade=중학생`이지만 `gradeBands=[]`입니다. 현재 정규화 로직의 중등 표현 감지에 `중학생`이 포함되지 않습니다.
- 학년군이 없는 나머지 두 항목은 ‘한/영 전환 도우미’, ‘AI Studio 교사 연수원’입니다. 학년군 누락을 모두 오류로 처리하지 말고, 학년 무관·교사용·미분류를 구분해야 합니다.

## 4. 랜딩페이지 진단

| 우선순위 | 관찰 / 소스 근거 | 사용자에게 미치는 영향 | 개선안 |
|---|---|---|---|
| 높음 | 공개 검색: `5학년 과학` 1개, `과학 5학년` 0개 | 같은 의도의 검색이 단어 순서에 따라 달라짐 | 단어별 검색과 과목·학년 필터 제공 |
| 높음 | 과목·학년군·대상·활동 유형이 데이터에 있으나 랜딩에는 검색·태그만 있음 | 교사가 익숙한 수업 조건으로 찾기 어려움 | 과목 → 학년군 → 활동 방식의 다중 조건 탐색 |
| 높음 | 대표 태그는 사용 빈도 상위 10개, 전체는 94개 | 수업·과학·추론 등 서로 다른 기준이 같은 층위에 놓임 | 분류 필터와 주제 태그를 분리 |
| 중간 | 114개 카드를 모두 렌더링 | 목록을 훑고 이전 위치를 되찾기 어려움 | 24개 단위 페이지 이동, 결과 수·정렬 제공 |
| 중간 | 1440×900 관찰에서 첫 카드 시작이 약 555px | 첫 화면에서 앱 제목과 활용 정보가 충분히 보이지 않음 | 상단 브랜드 영역을 줄이고 검색·대표 결과를 위로 이동 |
| 중간 | 검색·선택 태그는 컴포넌트 상태, 상세의 목록 링크는 `/` | 상세에서 명시적 목록 링크로 돌아오면 필터 보존 장치가 없음 | URL에 조건·정렬·페이지 저장, 목록 위치 복원 |
| 중간 | 카드에 설명·태그·과목·학년·메이커 노트·두 링크 | 목록 단계에서 반복되는 정보가 많음 | 카드에는 판단에 필요한 요약, 상세에는 긴 활용 설명 |

현재 검색은 전체 문구의 단순 포함 여부로 판단합니다. `과학`은 공개 화면에서 31개가 검색됐지만 구조화된 과학 과목은 29개입니다. 설명과 메모까지 검색하므로 서로 다른 수치이며 데이터 오류를 뜻하지 않습니다.

학년군 `5-6` 또는 `all`이면서 과학 과목인 앱은 로컬 스냅샷에서 18개입니다. 이는 ‘초등 5~6학년 과학’ 탐색 후보 수이며, 정확히 5학년 교육과정에 적합한 앱 18개라는 뜻은 아닙니다.

## 5. 권장 랜딩 구조

새로운 소개 전용 페이지를 한 단계 더 두기보다, 현재 홈을 자료실의 탐색 시작점으로 개선합니다. 재방문 교사가 즉시 검색할 수 있게 합니다.

```text
┌ Hong's Vibe Coding Lab ─ 앱 찾기 · 수업 모음 · 보관함 ┐
│ 수업에 맞는 앱을 찾아보세요                           │
│ [검색어____________________________________]         │
│ [전체] [학생 수업용] [교사 업무·도구]                 │
├───────────────────────────────────────────────────────┤
│ 교과 · 학년군 · 활동 방식 │ 결과 수  [정렬] [보기 방식]│
│ 선택 조건                │ 앱 카드 / 간결한 목록      │
│ 조건별 결과 수           │ 제목 · 대상 · 한 줄 활용   │
│ 주제 태그 검색           │ [자세히] [앱 열기] [저장]  │
│ [초기화]                 │ [이전] 1 2 3 … [다음]      │
└───────────────────────────────────────────────────────┘
```

위 항목 중 수업 모음·보관함은 초기 분석 당시 2차 범위로 두었지만, 구현 단계에서 반복 사용 지원까지 포함했습니다. 검색, 대상·과목·학년군 필터, 정렬·페이지 이동을 기본 탐색 축으로 유지합니다.

설계 규칙:

1. 서로 다른 분류끼리는 AND, 같은 분류 안의 복수 선택은 OR로 적용합니다. 예: `(과학 또는 수학) AND 초등 5~6학년`. 선택 조건과 해당 결과 수를 항상 보여 줍니다.
2. 학년 선택 시 `all`의 포함 규칙을 명시합니다. 교사용·미분류를 임의로 초등 전체에 포함하지 않습니다. 정확한 학년 필터는 별도 검수 데이터가 생기면 추가합니다.
3. 검색어는 공백 단위로 나누고 모든 단어의 일치를 기본으로 하되, 제목 정확 일치에 우선순위를 줍니다. 학년 범위·동의어 처리는 별도 규칙으로 정의합니다. 0개이면 조건 하나 해제, 비슷한 주제, 검색 예시를 제공합니다.
4. 정렬은 최근 등록·가나다순부터 시작합니다. 현재 `updatedAt`은 메타데이터 수정일일 수 있으므로 앱 자체 개선일로 표시하지 않습니다. 이용 데이터 없이 인기순을 만들지 않습니다.
5. 카드 정보는 실제 화면 썸네일, 제목, 대상·과목, 짧은 활용 설명과 실행 링크 중심으로 줄입니다. 긴 메이커 노트는 상세에서 읽게 합니다.
6. Windows 설치 도구처럼 브라우저 학습 앱과 실행 방식이 다른 항목에는 `Windows 설치형` 등 검증된 환경 배지를 붙입니다. 계정 필요 여부·권장 기기·시간은 조사 후 입력하며 추정치를 사실처럼 표시하지 않습니다.
7. 모바일은 왼쪽 필터 대신 `필터 N` 버튼으로 조건 패널을 열고, 선택 조건은 결과 위에 유지합니다. 결과는 1열 카드 또는 간결한 목록으로 제공합니다.
8. 최초 진입에는 편집자가 선정한 소수의 수업 모음을 선택적으로 제공하고, 검색 중에는 결과를 우선합니다. 추천 영역이 결과를 아래로 밀지 않게 합니다.

찜·최근 사용은 2차에서 로그인 없이 기기 내 저장으로 시작할 수 있습니다. 기기별 저장이라는 안내와 지우기 기능을 함께 둡니다. 학생 개인정보를 수집할 필요는 없습니다.

## 6. 관리자 페이지 진단과 제안

현재는 `현황·동기화 → 전체 등록 폼 → 전체 앱 라이브러리` 순서입니다. 라이브러리 검색·필터·페이지 이동이 없고, 편집 버튼은 선택 ID만 바꿉니다. 추가 로그인 조사에서 목록 중간 앱을 편집할 때 위쪽 폼은 바뀌지만 화면이 목록에 남는 현상을 확인했습니다. 미저장 입력도 앱 전환 시 확인 없이 사라졌습니다. 상세 측정은 11절을 참고합니다.

```text
┌ 앱 관리 ─ [검색________________] ─ [+ 새 앱 등록] ┐
│ 전체 · 공개 반영 대기 · 분류 확인 필요           │
│ [과목] [학년군] [상태] [정렬]                   │
├─────────────────────────┬───────────────────────┤
│ 선택 · 제목 · 과목       │ 선택한 앱 편집        │
│ 학년 · 수정일 · 반영상태 │ 기본 정보 / 수업 분류 │
│ 앱 목록 25개            │ 썸네일 / 상세 정보    │
│ [이전] 1 2 3 … [다음]   │ [미리보기] [저장]     │
├─────────────────────────┴───────────────────────┤
│ 공개 반영 대기 N건 [변경 내역 보기] [공개 반영]  │
└─────────────────────────────────────────────────┘
```

- **앱 목록을 기본 화면으로:** 제목·URL·태그 검색, 과목·학년·반영 상태 필터, 수정일 정렬. 기존 앱 수정은 검색 후 바로 진입합니다.
- **편집을 목록 옆에:** 넓은 화면은 목록+편집 패널, 좁은 화면은 별도 편집 화면과 목록 복귀를 사용합니다. 폼은 섹션별로 나누고 저장·취소를 찾기 쉬운 위치에 둡니다.
- **입력 보호:** 저장하지 않은 상태에서 앱 전환·닫기를 하면 변경 내용 보존 또는 폐기를 선택하게 합니다. 이 확인은 실제 미저장 상태일 때만 표시합니다.
- **표준 분류 입력:** 현재 자유 입력인 과목·학년을 표준 선택으로 보완합니다. 별칭·주제 태그는 유지하고, 미분류 항목을 별도 목록에서 검수합니다.
- **저장 전 공개 카드 미리보기:** 줄임 표시, 학년·과목 배지, 실제 실행 링크를 확인합니다. 단순 필드 오류는 해당 입력 옆에서 안내합니다.
- **삭제 실수 방지:** 현재 태그 삭제에는 확인이 있으나 앱 삭제는 바로 서버 액션으로 이어집니다. 앱 이름을 보여 주는 확인을 우선 추가하고, 보관·복원은 데이터 모델 변경을 포함한 후속 기능으로 구분합니다.
- **일괄 작업:** 2차에서 선택 항목의 태그 추가·제거, 분류 변경을 제공합니다. 변경 대상 수와 전후 차이를 먼저 보여 줍니다. 대량 삭제는 초기 범위에서 제외합니다.
- **보조 작업 분리:** 백업·실행 로그·로그아웃은 메뉴로 정리하고, 등록·저장·공개 반영에 시각적 우선순위를 줍니다.

## 7. 저장과 공개 반영을 명확히 구분

현재도 수정 건수, DB/스냅샷 건수, 최근 실행 상태와 GitHub Actions 링크를 제공합니다. 이 기반을 유지하면서 기술 용어보다 관리자에게 필요한 상태를 먼저 보여 줍니다.

```text
앱 정보 저장 → 공개 반영 대기 → 반영 요청 → 처리 중 → 공개 확인 완료
                                            └→ 실패 / 확인 필요
```

- 저장 완료 안내: `저장했습니다. 공개 페이지에는 아직 반영되지 않았습니다.`
- 공개 반영 대기 목록: 어떤 앱의 무엇이 달라졌는지 확인합니다.
- 반영 작업 성공과 실제 공개 사이트의 새 내용 확인을 구분합니다. 실행 성공만으로 `공개 확인 완료`를 표시하지 않습니다.
- 실패 시 데이터 저장 성공 여부, 실패 단계, 실행 기록, 재시도 가능 여부를 표시합니다.
- 전역 일괄 반영이면 버튼에 반영 대상 전체 건수를 명시합니다. 앱별 선택 반영은 현재 동기화 구조와 별도의 설계가 필요합니다.
- ‘공개/비공개’ 상태는 현재 모델에 없으므로 단순 배지 변경으로 해결할 수 없습니다. 비공개 기능이 필요하면 내보내기·상세 경로·검색엔진 노출까지 설계합니다.

VoiceOver 구현·검증은 제외합니다.

## 9. 구현 시 보존할 것과 비용 통제

- 홈의 정적 배포, 공개 스냅샷, 기존 앱 상세 주소, sitemap·구조화 데이터·FAQ·llms.txt를 유지합니다. 검색 UI 변경과 DB 실시간 조회 전환을 묶을 이유는 없습니다.
- 카드에는 이미지 지연 로딩과 `content-visibility`가 이미 있습니다. 긴 목록이라는 사실만으로 모든 이미지를 동시에 내려받거나 현재 성능이 나쁘다고 단정하지 않습니다.
- 114개 규모에서는 구조화 필터·로컬 검색을 먼저 검토합니다. 벡터 검색, AI 추천, 별도 검색 서버는 필요성이 확인된 뒤 판단합니다.
- 필터 URL 도입 시 기존 상세 주소는 유지하고, 임의의 필터 조합이 무한히 검색엔진 색인되지 않게 canonical·색인 규칙을 설계합니다.
- 구현 시 `admin-workspace.tsx`는 499줄로 줄이고 동기화 상태·일괄 선택·미리보기·페이지네이션을 별도 파일로 나누어 프로젝트의 500줄 기준을 적용했습니다. `globals.css`는 기존 전역 규칙을 유지한 채 기능별 블록을 추가했습니다.
- 업데이트 내역 버튼과 변경 기록을 유지합니다. 다음 필수 행동의 강조는 필요할 때 하나만 사용하고, 다수 카드 전체가 동시에 깜빡이지 않게 하며 모션 감소 설정을 존중합니다.
- 썸네일은 앱의 실제 화면을 우선합니다. 생성 이미지는 수업 모음 표지 등 분위기를 전달하는 곳에 선택적으로 사용하고, 실제 기능을 오인시키지 않게 합니다.

## 11. 관리자 로그인 후 추가 분석

동일 날짜에 사용자 승인으로 로그인했습니다. 인증 정보는 보고서·스크린샷에 기록하지 않았습니다. 앱 편집 선택과 브라우저 폼의 임시 입력만 수행하고, 저장·삭제·태그 삭제·썸네일 교체·동기화·백업 실행은 하지 않았습니다.

### 11.1 실제 확인 상태

- 관리자 앱 114개, 태그 94개, DB/정적 스냅샷 표시 114/114개.
- 동기화 대기 없음, 마지막 스냅샷 2026. 9. 1., 최근 실행 상태는 완료·성공으로 표시.

- 재접속 후에도 114개, 원래 앱 제목, 동기화 대기 없음이 유지됐습니다. 임시 입력 표시는 남지 않았습니다.

### 11.3 미저장 입력 재현 절차

1. 목록의 ‘학급 업무 체크리스트’를 편집 모드로 선택.
2. 제목에 임시 확인 문구를 덧붙이고, 폼에 입력된 사실 확인. 저장 버튼은 누르지 않음.
3. ‘교실 자리 바꾸기 도우미’ 편집 선택. 별도 확인 없이 해당 앱으로 전환됨.
4. 다시 ‘학급 업무 체크리스트’ 선택. 임시 문구가 사라지고 원래 제목으로 돌아옴.
5. 관리자 페이지 재접속. 원래 제목과 동기화 대기 없음 확인.

### 11.4 기존 제안의 조정

관리자 개편은 다음 두 단계로 나누는 것이 적합합니다.

```text
1차: 입력 손실 방지 + 좁은 화면 넘침 해결 + 목록 검색 + 편집 위치 연결
                              ↓
2차: 목록 중심 화면 전환 + 태그 검색 + 저장 바 + 공개 반영 대기 목록
```

분류 사전 정비는 함께 준비하되, 미저장 입력 손실과 좁은 화면 문제는 전체 리디자인 완성을 기다리지 않고 먼저 해결할 가치가 있습니다. 이 우선순위를 반영해 구현 결과를 12절에 기록했습니다.

동기화 건수와 실행 기록 안내는 실제로 동작하고 있어 유지할 기반입니다. 현재 대기 항목이 0건이므로 대기·진행 중·실패 상태의 실제 UX는 이번 현장 조사에서는 확인하지 못했습니다. 구현 후 자동 테스트로 해당 상태 분기를 검증했습니다.

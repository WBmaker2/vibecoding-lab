# 실제 페이지 캡처 썸네일 설계 문서

## 개요

`Hong's Vibe Coding Lab`의 관리자 등록 흐름에서 `앱 링크만 입력하면 실제 사이트를 자동으로 캡처해서 썸네일로 저장`하는 기능을 추가합니다. 기존의 메타 이미지 우선 정책은 유지하되, 소셜 미리보기 이미지가 없을 때만 실제 페이지 캡처를 시도하고, 그마저 실패하면 플레이스홀더로 안전하게 fallback 합니다.

## 합의된 방향

- `auto` 모드는 그대로 유지합니다.
- `auto` 모드 내부 동작만 아래 순서로 확장합니다.
  1. `og:image` / `twitter:image` / 아이콘 메타데이터 사용
  2. 서버에서 실제 페이지를 열어 1200x630 비율로 캡처
  3. 캡처 실패 시 플레이스홀더 사용
- 등록 실패보다 썸네일 fallback을 우선합니다.
- 캡처 이미지가 성공하면 기존 `thumbnailUrl`처럼 저장되어 공개 카드에서 그대로 렌더링됩니다.

## 기술 설계

### 1. 캡처 유틸

- 새 서버 전용 유틸에서 `playwright-core`와 서버리스용 Chromium을 동적으로 불러옵니다.
- 대상 URL은 `http` 또는 `https`만 허용합니다.
- 캡처 뷰포트는 `1200x630`으로 고정합니다.
- 페이지 로딩 후 짧은 안정화 대기 시간을 둔 다음 PNG로 캡처합니다.

### 2. 저장 방식

- 캡처 PNG는 기존 수동 업로드와 동일하게 공개 접근 가능한 URL로 저장합니다.
- `BLOB_READ_WRITE_TOKEN`이 있으면 `Vercel Blob`에 업로드합니다.
- 토큰이 없는 로컬 환경에서는 개발 편의를 위해 `data:` URL fallback 을 허용합니다.

### 3. 등록 흐름 연결

- `resolveThumbnailInput()`의 `auto` 경로에서 메타 이미지가 없을 때 캡처 유틸을 호출합니다.
- 미리보기 요청 자체가 실패해도 캡처는 계속 시도합니다.
- 캡처까지 실패하면 동적 썸네일 URL을 만들지 않고 `thumbnailUrl: null`인 플레이스홀더로 내려갑니다.

## 오류 처리 원칙

- 캡처 실패는 등록 실패로 올리지 않습니다.
- 잘못된 URL, 브라우저 실행 실패, Blob 업로드 실패는 모두 플레이스홀더 fallback으로 흡수합니다.
- 운영 환경에서 Chromium 제약이 생겨도 기본 썸네일로 내려가므로 공개 아카이브는 계속 동작합니다.

## 검증 계획

- `resolveThumbnailInput()` 테스트에 `메타 이미지 있음`, `메타 없음 + 캡처 성공`, `메타 요청 실패 + 캡처 성공`, `캡처도 실패` 시나리오를 추가합니다.
- 관련 Vitest 테스트, `npm run lint`, `npm run build`로 검증합니다.
